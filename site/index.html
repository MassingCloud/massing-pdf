massing-pdf

A construction drawing review engine you can build on.

PDF viewing, AEC markup, calibrated takeoff, issue pins, revision compare and XFDF/BCF interchange — behind a small plugin kernel. Framework-agnostic, offline, and clean under a strict Content-Security-Policy.

Open the live demo Source on GitHub

The demo generates its own sample drawing set in the browser and stores markups in IndexedDB. Nothing is uploaded, and it keeps working with the network off.

What it does

A markup here is a record, not ink. Rendering is one projection of it; XFDF, BCF, CSV and a flattened PDF are others — so a review survives leaving the tool it was made in.

Review

Tiled rasterisation, selectable text, pen pressure with palm rejection, and the AEC markup set — clouds, callouts, stamps, dimensions.

Takeoff

Calibrated distance, area, perimeter, angle and volume. Re-calibrating re-derives every measurement on the page instead of invalidating them.

Issues

Pins following the BCF model, with status, assignee and due date, so topics round-trip with the BCF managers inside Revit, Navisworks, Solibri and Tekla.

Revisions

Overlay compare with auto-alignment, change clustering, auto-clouding, and slip-sheet migration with a review queue.

Specifications

CSI section and clause parsing, requirement extraction, and drawing→spec callout detection — with a per-line correction path for what the heuristics misread.

Collaboration

Optimistic concurrency with both sides of a conflict carried to a dialog, plus presence and advisory per-markup leases over a transport you supply.

Install

The @massingcloud npm scope is not claimed yet, so npm i does not resolve it. That blocks nobody — three routes work today, and all three are verified. 

# A pinned git ref — best while iterating
npm i "github:MassingCloud/massing-pdf#main"

# Or a packed tarball — best in CI: dist/ is prebuilt, no install scripts run
npm pack && npm i ./massingcloud-pdf-viewer-0.1.0.tgz
import { createViewer } from "@massingcloud/pdf-viewer";
import "@massingcloud/pdf-viewer/style.css";
import workerUrl from "pdfjs-dist/build/pdf.worker.min.mjs?url";

const viewer = await createViewer({ container, workerUrl, author: "A. Reviewer" });
await viewer.load({ url: "/sheets/A-201.pdf", name: "A-201" });

Zero runtime dependencies. pdfjs-dist is a peer and pdf-lib an optional one, so their versions stay yours — see publishing.md for the third route and the one npm 11 wrinkle.

What it does not do

Stated because a capability list nobody contradicts is worth less than one that admits its edges. The full version lives in the roadmap.

  • No bundled OCR engine, deliberately. Scanned sheets need a provider you supply. Naming a default would put that choice in the library instead of the host.
  • No realtime transport. Presence and locking are built; the socket is yours, for the same reason.
  • Accessibility is conformant but unaudited. Keyboard operation and accessible naming are verified against the computed accessibility tree on every build — but nobody has run JAWS, NVDA or VoiceOver against it, and no third party has checked it.
  • Not yet on npm, and version 0.1.0 signals the API may still move.
